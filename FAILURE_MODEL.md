# Failure model and recovery contract

This is a current-code failure-window guide, not a claim of remote exactly-once. Each row follows the same sequence: failure → naive risk → detection → authority → recovery → remaining limit. The current architecture is summarized in [docs/architecture.md](docs/architecture.md); test boundaries are described in [docs/testing.md](docs/testing.md).

| Failure | Why the naive implementation is unsafe | Detection | Durable authority | Recovery | Remaining limitation |
|---|---|---|---|---|---|
| PostgreSQL/Saver/Store unavailable at startup | A compiled graph without persistence can answer now but lose HITL/resume/conversation correctness | R1 component preflight and `/health` 503 | Postgres Saver/Store and `RuntimeCapabilities` | Keep process live for diagnostics; reject webhook 503, repair dependency and restart to rebuild durable graphs | Restart is the supported recovery model; no silent in-memory production downgrade |
| Duplicate Telegram webhook or crash after HTTP custody commit | Process-local set disappears on restart; duplicated update could repeat Todo/approval | `(bot_identity, update_id)` uniqueness, receipt/business proof | `TelegramInboundReceipt`, `TelegramBusinessOperation`, Saver/ActionExecution | ACK only after receipt commit; claim/replay the same receipt and suppress completed operation | Bot update identity is not an action authorization or outbound delivery confirmation |
| Todo DB mutation committed, receipt/graph completion lost | Re-invocation can create a second task | Stable operation/child action ID and joined proof | Todo DB + R4 business operation or `ActionExecution(parent:todo)` | Return the committed result; cross-domain child Todo and ledger commit atomically | Non-DB provider actions need separate reconciliation |
| Telegram chunk send started, response lost/cancelled | A retry may duplicate a message already accepted remotely | `SENDING` lease expiry / timeout becomes `UNCERTAIN` | R4 delivery/chunk/attempt rows | Bounded retry of only unconfirmed chunk, with uncertainty visible; confirmed chunk is never resent | Bot API offers no request idempotency key/readback for unknown send; **not exactly-once** |
| Scheduler process down, duplicate fire or active renderer crash | An in-memory job or permanent pre-send claim loses a Rundown/reminder | Stable occurrence key, lease/fence, backlog snapshot | `ScheduledOccurrence` + R4 shared outbox | Bounded catch-up/reclaim; render once into immutable intent, then shared chunk dispatch | Expired/irrelevant reminder may stop as `EXHAUSTED` while remote chunk remains `UNCERTAIN` |
| Google create accepted, response/local commit lost | A new random event ID on retry creates duplicates | Armed evidence `IN_FLIGHT/UNCERTAIN`; exact ID GET + marker/postcondition | `CalendarActionEvidence`, `ActionExecution`, exact Google resource | Reconcile same deterministic ID; match confirms, conflict parks, verified absence permits bounded same-ID retry | Delayed visibility/access loss can require review; local DB and Google do not commit atomically |
| Google update/delete ETag changed after approval | Fetching latest ETag and blindly writing violates the approved version and can overwrite manual changes | `If-Match` 412 or exact readback mismatch | Saver-approved baseline + CalendarActionEvidence + Google ETag | Park for review; new proposal and approval must capture a new baseline | Observed desired state does not prove which actor caused it; recurring multi-resource writes unsupported |
| Calendar parent confirmed late after approved cross-domain workflow waits | If `UNCERTAIN` ends graph, approved child Todo is never executed | Parent evidence+ledger joined with waiting locator | Saver/HITL + `CalendarDependentContinuation` | Recovery wakes original checkpoint; executor rechecks parent before child | Wakeup alone never grants Todo authorization |
| Crash before/during dependent Todo after Calendar confirmation | Replaying node could repeat Todo or Calendar write | Stable parent evidence and `parent_action_id:todo` proof | Calendar evidence + Saver + atomic Todo/child ActionExecution transaction | Skip confirmed Calendar mutation; child transaction commits both or neither, replay returns same result | This covers current single child, not arbitrary multi-effect sagas |
| Stale/superseded/forgotten memory retrieved | Old conversation may override corrected fact or current domain DB | Source IDs, supersedes/tombstone/currentness, context selection | R3 full checkpoint/transcript projection/structured memory; domain DB remains higher authority | Filter stale before model; rebuild derived index under suppression; degrade explicitly if source unavailable | Summary/retrieval remain lossy; arbitrary answer entailment not mechanically proven |
| Calendar/Gmail/Todo/Profile source unavailable during Meeting Prep | Treating unavailable as empty invents certainty; stale memory may replace current provider fact | Collector availability and exact Calendar revalidation | Source-specific Google/Gmail/Todo/Profile/R3 identities, typed evidence envelope | Qualify missing source or return unavailable; reject unsupported claims/citations | Real combined private Calendar+relevant Gmail+model acceptance is `SAFE_FIXTURE_NOT_FOUND` |
| Ambiguous/destructive user intent or missing target | A high-confidence model can guess delete or fill a schema with an ungrounded target; HITL arrives too late | `clarify` route, literal destructive/slot guard, exact source resolution | User text + Saver-selected context + current domain target + HITL | Clarify/fail closed before mutation; valid recent referent may proceed to exact source check | Bounded multilingual corpus is not an all-language guarantee; Calendar-read→Todo is not yet a supported typed composition |
| Wrong route or genuinely missing capability | Exposing every tool can increase wrong calls; over-scoping can hide needed capability | R7 route/plan and full Todo-loop A/B, clarification eval | Existing route/workflow state and execution-side scope | Clarify or use supported typed path; no automatic all-tools fallback | Progressive/semantic/selector have no present same-domain production target; migrate only after a measured capability miss |
| Web browser disconnects after submitting a Chat/form run | Cancelling with the HTTP connection could lose or repeat a business turn | Committed `WebRequest`, stable idempotency key/turn ID, status polling | WebRequest + Saver checkpoint + ActionExecution/Todo operation proof | Leased worker continues; after restart the same run/fence is reclaimed or reconciled and queried by run ID | A submitted run can remain queued or waiting for approval/external reconciliation; it is not a synchronous success guarantee |
| Chat routing model unavailable before Web business dispatch | Treating every wrapped `ValueError` as user ambiguity falsely marks an outage as a completed clarification | Wrapped non-validation provider error category; run state and safe error | WebRequest state; no Saver/domain action has begun | Persist `FAILED` with `RoutingModelUnavailable`, display unavailable and allow a deliberate new request after recovery; true target ambiguity still clarifies | A failed external model call is not a successful answer; the earlier V3.3 502 was corrected externally and current-head real-model Web acceptance passed |
| Web Todo mutation commits before worker/result completion | Replaying an unproved tool call could duplicate a Todo | Stable Web turn/tool action identity and joined DB proof | Todo row + ActionExecution in one short transaction | Replay returns existing local outcome rather than inserting a second task | Does not make Google or Telegram side effects transactional with PostgreSQL |
| Web session expires or cross-user approval URL is replayed | A browser-provided user ID/action ID could expose another user's task or approve their proposal | Server session owner, CSRF/Origin, checkpoint/action ownership and version checks | WebCredential/WebSession + Saver HITL + ActionExecution | Return 401/403/404/409; reauthenticate or reload the current proposal before a new decision | Trusted HTTPS origin and proxy configuration are deployment responsibilities; no anonymous Web access |
| Calendar is changed after a Web form's list view | Binding the list result or approval-time fresh ETag could approve a different version | Exact event GET and ETag comparison at form admission; Google `If-Match` on write | Saver-approved proposal, CalendarActionEvidence, exact Google event | 412/conflict requires new exact read and new approval; no silent latest-ETag overwrite | Current-head bounded real Google week/detail/reload **read-only** UI passed; E4 Fake Provider and historical R5 write E5 remain distinct evidence |

## Operational interpretation

`/health` answers whether the process can safely take the configured product traffic; `/health/messaging` answers aggregate custody/backlog/degraded delivery without private payload. A remote outage with durable backlog differs from a broken PostgreSQL custody store. Shutdown closes admission and new claims first, drains active work under one monotonic deadline, then cancels locals while leases remain recoverable. R4 terminal redaction removes private replay bytes only after terminal dependencies and age horizon; restoring a backup predating user deletion requires an external deletion authority/reapplication before claims, which this repository does not implement.

The three negative claims to remember are: **checkpoint ≠ search index**, **local ledger/outbox ≠ remote truth**, and **a model's route/citation ≠ authorization/evidence**.
