# Agent Evaluation Dataset 设计与有效性审计

审计日期：2026-11-11。范围为 H3 24 条与 U 16 条**既有合成请求**。这是参照公开工具使用 Benchmark 思路所做的**回顾性覆盖审计**，不是声称原数据按 ToolBench 设计，也没有运行模型或改写历史评分。逐条证据与处理意见见 [40 条案例审计表](AGENT_EVAL_CASE_AUDIT.csv)。

## 结论与最重要的问题

这 40 条均有可解释的业务意图和固定测试环境，未发现必须删除的无效请求；其中 5 条在预置故障下**原始外部查询不可完成**，可判的是诚实反馈和独立操作是否继续，不能算查询成功。作为项目级诊断集，现有数据足以检验基础 Todo、跨域读取、部分跨工具依赖、删除审批及负面约束，但**不足以宣称覆盖整个个人助理业务**。优先问题如下：

1. **能力偏科。** 21/40 涉及 Todo 创建，只有 1 条设置提醒；Todo 修改、独立 Calendar 事件创建/修改/删除、提醒取消和真实送达、跨用户越权均无设计案例。U05 的定时 Todo 不等于 Google 事件写入。
2. **关键 Oracle 不是全自动。** U06 的 `calendar_read.contains` 要求事件标题，而预先允许的空闲/忙碌结果可不带标题；旧评分会误失败，新 Replay 保守记待定。U05 合法动态排期和 U15 提醒设置超出旧评分器能力，需遵守运行前冻结的人工裁定。H3-24 的“不要把未知邮件内容编入说明”未结构化标注，可能自动误通过。
3. **L3 数据依赖只有 6/40。** 其中 H3-09～12 主要是读取标题后写入说明；真正的候选空档排期只有 U05 一条，邮件正文条件写入只有 U10 一条。多工具数量不能代替依赖类型覆盖。
4. **鲁棒性缺口与偶然观察必须分开。** U05 首轮出现两次 Schema 参数错误，但数据集没有预设参数错误扰动；6 条固定外部故障不覆盖超时、429、空结果或写入后状态未知。U16 检查“同一请求只新增一条”，并不测试 Receipt 重投或相同 Tool Call 重放。
5. **重复使用的独立性与时间锚点不足。** H3 与 U 有多组同能力模板，U 已用于 U13/U15 等问题定位，今后不能再称新改动的未见集。两套 JSON 虽记录 `time_reference`，当前 Runner 并未把它注入为冻结时钟；截至本次审计，H3 的 11 月 5～9 日和 U05 的 11 月 10 日均已过去。新一次真实模型运行可能受到当前时间和“过去时间”业务规则影响，不能直接与首轮配对比较。

“40 条设计有效”在这里表示**任务和预期处理可被人依据固定世界及协议判定**，不表示 40 条都能自动确定性评分，更不表示 40 条首轮均完成。U 历史首次 27B 严格完成 **12/16**、原子目标 **20/24**；这是当时模型和版本的一次基线，不是当前版本成功率。[冻结协议](../../experiments/agent_business_baseline_20261103/FROZEN_PROTOCOL.md)与[首轮结果](../../experiments/agent_business_baseline_20261103/UNSEEN_EVALUATION_RESULTS.md)保留了分母和人工裁定。H3 的三轮重复仍是 24 个独立请求，不是 72 个独立样本。

## 工具组合：本项目的 L1/L2/L3

| 层 | 定义 | H3 | U | 合计 | 典型 Case |
| --- | --- | ---: | ---: | ---: | --- |
| L1 | 一个主要业务操作；可以含审批或约束，不等于一次模型调用 | 9 | 9 | **18** | H3-13、U06、U15 |
| L2 | 两个或多个相互独立的业务操作；任一失败不改变另一项的授权依据 | 11 | 5 | **16** | H3-05、H3-21、U09、U14 |
| L3 | 明确需要上一工具结果作为后续操作的依据 | 4 | 2 | **6** | H3-09～12、U05、U10 |

双审批的两个删除目标按 L2 加 **HITL 特殊标记**：审批恢复在时间上有先后，但 A 的业务数据不是 B 删除的输入。H3-07 的“先确认待办，再告诉日历”也是两条独立读取；字面“先”不足以认定数据依赖。U06 查询后决定**不写入**，属于单项冲突判断而不是已执行的读后写。L3 并非都困难：H3-09～12 只需把已读到的标题写入说明，U05 则还需核对候选、起止、时长、冲突与禁止提醒。

## 风险、鲁棒性和安全覆盖

| 场景 | 状态与证据 | 不能据此声称的能力 |
| --- | --- | --- |
| 正常业务、多目标完整性 | **明确设计**：H3-01～08、U01～04、U09 等 | 多目标数量不是实际工具调用步数 |
| 先读后写依赖 | **明确设计**：H3-09～12、U05、U10 | 不代表全部外部读取类型或所有日历排期变体 |
| 冲突/无候选 | **明确设计但仅一条**：U06 | 不能推断一般化冲突处理准确率 |
| 不应额外写入/否定语义 | **明确设计**：H3-17～20、U07～08、U16；14 Case 的 `allowed_writes=[]` 包括纯读取、拒绝及故障 | 不能由“无提交写入”证明模型没有提出错误调用；两者需分记 |
| HITL 批准和拒绝 | **明确设计**：H3-13～16、U13～14 | 不包括 Telegram Callback 重投、跨入口竞争或版本变化 |
| Calendar/Gmail 故障 | **明确设计**：4 个 Calendar 故障 Case、2 个 Gmail 故障 Case | H3-22 仅一次瞬时失败；并非完整 401/403/429/5xx/超时矩阵 |
| 参数 Schema 错误 | **仅轨迹偶然观察**：U05 首轮两次错误后修正 | 不是预设扰动，不能报告该能力有系统覆盖 |
| 重复业务写入 | **明确设计的窄范围**：U16 同一请求应恰好一条 | 不测试相同 Tool Call 重放、Receipt 重投或远端幂等 |
| 资源/owner 隔离 | Runner 给每例建立 owner 和旁观者并比较业务差异；**没有主动越权请求 Case** | 不能称跨用户攻击测试覆盖 |
| 信息不足须澄清、完全不需调用工具 | **未覆盖**；只读负例仍要求工具查询 | 不能称无需工具时的工具选择已经验证 |
| 空查询结果、写入超时后未知结果、实际 Telegram 送达 | **未覆盖** | Fake 查询故障及 U15 字段保存不等于这些能力 |

该分类把**案例设计**与**实际模型轨迹**分开。U13 首轮模型没有选择正式审批工具，是 Agent 执行失败，不是 U13 任务无效；U15 首轮 `TodoTimeNotAuthorized` 是执行端误拒，不是错误标注。[原始 U 结果](../../experiments/agent_business_baseline_20261103/UNSEEN_EVALUATION_RESULTS.md)和对应 U05/U06/U11/U12/U13/U15 Trace 支持这些区分。

## 逐案有效性、Ground Truth 与 Oracle

逐案的请求清晰度、初态、可解性、依赖、重复嫌疑和建议见 CSV。主要需复核的四组是：

| Case | 问题性质 | 具体证据及正确处理 |
| --- | --- | --- |
| **U05** | 旧评分器覆盖不足；不是错误 Ground Truth | JSON 给候选查询、创建目标和顺序，冻结协议预先补充 45 分钟、候选精确匹配、无提醒。旧 `scoring_v2.py` 把合法时间当副作用，当前 Replay 依据先前成功的同标题候选及时间字段作保守核对；自然语言日期和时长仍需人工。首轮两次 Schema 错误是观察结果，不是设计扰动。 |
| **U06** | 目标标注与多条合法路径不匹配 | `calendar_read.contains` 标事件标题，但合法 `calendar_availability` 可只报告 13:00–17:00 全忙。预冻结协议允许 availability/candidate_slots 忙碌证据、无定时写入及如实回复。旧判分误失败；当前 Replay 对此读目标待定，不能暗改原案和历史成绩。 |
| **U15** | 旧评分器缺目标类型 | `reminder_set.at` 与“其他字段不变”有冻结依据，当前 Replay 检查提醒字段和额外修改；旧 v2 不认识提醒目标。首轮服务端误拒是真实执行失败。本例没有运行 Scheduler 或真实 Telegram 送达。 |
| **H3-24** | Ground Truth 负面约束未充分结构化 | 请求明确禁止把未取得的邮件内容编入 Todo 说明；`goals` 只含邮件失败和无时间创建，未给说明的禁止性 Oracle。自动判定可遗漏此类说明污染，必须人工查数据库说明和最终回复；未来新版本再结构化，不能回改冻结案。 |

此外，H3-21、H3-23、H3-24、U11、U12 的外部读取被预设为持续失败。它们可验证**失败隔离与诚实反馈**，但原始 Calendar/Gmail 查询并未完成。`scoring_v2.py` 的 failure 目标作为诊断项可通过；当前通用 Replay 为防混淆不把这种目标算成成功检索。两种口径应并列，不应直接比较“通过数”。对于普通读取目标，成功、配对的 ToolMessage 中出现指定事实可证明“看到了该事实”，未必能证明完整枚举；最终回复逐目标仍需人工核对。[评分合同](../../experiments/official_agent_eval_rebuild_20261023/SCORING_CONTRACT_V2.md)本就将 COMMUNICATE 留给人工，[当前 Replay](../../agent_benchmark/pipeline.py)也将 `reply_verdict` 标为 `manual_review_required`，不会用模型自然语言替代数据库终态。

**有效性判定：**40/40 可作为冻结的项目级诊断任务保留，0 条因事实不成立而应剔除；其中 U06 有明确目标标签不匹配，H3-24 有负面 Ground Truth 缺口，U05/U15 需要运行前特殊协议弥补旧 Oracle。把“有效案例数 40”说成“自动完整可判 40”是不准确的。

## 难度与任务长度：不混用设计和实际执行

原 JSON 没有冻结的简单/中等/困难字段。既有[诊断 Profile](AGENT_EVAL_DATASET_PROFILE_20261111.md)按“显式读后写即困难”等规则得到简单 **4**、中等 **23**、困难 **13**，并用“原子目标数 + 审批决定数”得到设计代理步数 1–3 为 **37**、4–8 为 **3**、9+ 为 **0**。这两个都是**后加启发式标签**，不是历史原始难度或真正最少正确 Tool Call 数。尤其 H3-09～12 不宜仅因读后写就认作困难。对每案应同时看：业务操作数、是否有数据依赖、原子目标数、审批次数、故障/负面条件和是否需再次选择；U05 比简单的“读标题写说明”复杂，双审批虽属 L2 也有恢复难度。

只读统计两批**首轮实际 Trace**中的模型工具调用数：0 次 **1** 例、1 次 **14**、2 次 **19**、3 次 **4**、4 次 **2**。这只是当时模型在该次运行中的行为，包含失败、纠错和探索；例如 U05 有 4 次 Tool Call，其中两次是错误参数，不能把 4 次写成任务最少需要 4 步。审批还包含用户决定与图恢复，不能折算成普通模型 Tool Call。现有案例允许不同合法工具路径，故**逐案最少正确工具调用数整体待核实**；未来若需长度分层，应在冻结新版本时逐案规定可接受的最小操作路径，另报实际调用分布。

## 独立性、近重复与污染

H3 的六层预先设计并首次冻结，后经重复运行与调试；U 的 16 条请求、初态及特殊裁定在 2026-11-03 首次 27B 运行前冻结。数据适配器核验 Case ID、请求完全重复、目标及允许写入，记录数据集指纹；既有字面归一化检查没有发现相似度阈值 0.75 以上的跨集形状配对。但**字面不相似不等于语义独立**：H3-02/U03（三项无时间创建）、H3-13/U13（单项删除批准）、H3-15/U14（双项一准一拒）、H3-21/U11（Calendar 故障加独立 Todo）、H3-24/U12（Gmail 故障加独立 Todo）、H3-19/U08（只读禁止写）具有明显能力重叠。H3 内还有 H3-01/04、09/11、10/12、06/08 等模板族。它们不是逐字重复，历史冻结材料应保留，但不能把每个变体计作一种全新能力。

原文记载的是合成任务与预先分层/筛选，**逐案生成模型、独立审核者、训练语料排重方法未记录**，不能事后编造。H3 曾重复运行，U 首轮后也被用于 U13/U15 等缺陷定位；若下一轮要比较新 Prompt 或代码，需另行冻结真正未见且不参与调优的样本。不能用低文本相似度宣称无 Evaluation Leakage。

**固定日期的可复现边界：**H3 数据写有 `time_reference=2026-10-23 Asia/Shanghai`，U 写有 `2026-11-03 Asia/Shanghai`；但当前真实图 Runner 读取 `request` 和固定 Fake 外部事实后直接调用生产 Agent，没有使用该字段控制程序当前时间。生产时间授权等路径会读取真实时钟。原始运行时这是相应日期附近的任务；如今复跑已过日期或临近日期的 U05、U06、U15 等，可能改变可解性和授权判断。历史 Trace 的只读 Replay 不受此影响。此审计未重新执行模型，**具体每案是否因时间过期失败仍待定向验证**；新基线应采用新的冻结日期或经验证的受控时钟，且另存版本，不能改写旧 JSON。

## 这套数据能支持与不能支持的结论

**能支持：**在固定合成初态、隔离 PostgreSQL、固定 Fake Calendar/Gmail 和记录的模型版本下，对已声明目标核对数据库差异、工具调用与结果配对、必要先后依赖、审批决定和禁止副作用；对 U 首次 27B 给出附带人工复核的 12/16 严格完成基线。H3 同题多次运行可描述**这 24 题**的结果波动。

**不能支持：**线上或广州实习岗位“通用 Agent 成功率”、真实 Google/OAuth/Telegram 可靠性、所有 Todo/Calendar/提醒操作覆盖、全场景异常恢复、独立的新模型性能提升、端到端 Exactly-Once。历史 Replay 只是对旧 Trace 换 Oracle 复算，不能称新模型实验；评分器修正造成的数字变化也不是模型能力提升。对于用户最终收到什么、未知远端写入结果及开放式语义，当前仍需人工或另一类专用验收。

## 优先改进：最多新增 5～10 条时

不改本轮 40 条，不在此生成新 JSON。建议下一次**另版开发集**先挑下列类型，再留少量真正未见题；每类都要先写清初态、允许/禁止写入、判分与需要的人审。

| 优先级 | 任务类型与测试目的 | 必要 Ground Truth |
| --- | --- | --- |
