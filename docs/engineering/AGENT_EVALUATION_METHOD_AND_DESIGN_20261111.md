# Telegram Personal Assistant：Agent Evaluation 方法与设计说明

日期：2026-11-11。本文规范**已有实验的解释和报告方式**，不改写历史数据、运行结果或冻结评分合同。本轮只对现有离线分析增加设计覆盖统计与明确的指标分母，未运行真实模型。主要参考：[Zero2Agent《Agent 评测》](https://onefly.top/zero2Agent/learn-agent-training/05-agent-eval/index.html)的“指标体系”“评测环境搭建”“评测集的构建”“评测陷阱”四节。文章面向 Agent 训练，所举比例与大规模用例数量是建议，不能直接成为个人助手项目的及格线。

## 1. 评测目标、数据来源与适用范围

| 数据 | 独立任务 | 设计和用途 | 不能混用的地方 |
| --- | ---: | --- | --- |
| H3 分层保留集 | 24 | 六个预声明风险层，每层四条人工编写的合成请求；同一批曾重复运行三轮，用来诊断调用波动 | 三轮不是 72 条独立样本；首次业务与回复均正确 17/24，不等于“故障处理场景合同通过”19/24 |
| U 冻结未见集 | 16 | 2026-11-03 首次模型运行前固定请求、初态、许可写入和特殊人工裁定；当时 27B 的一次基线 | 历史严格完整 12/16、原子目标 20/24；后续针对 U13/U15 的修复不能算作新的未见成绩 |
| 本轮 Replay | 同一 U 的 16 条旧 Trace | 重新计算**确定性可判部分**，检查工具与状态证据、补分母和覆盖统计 | 没有再次调用 Qwen；自动 11 通过、4 失败、1 待定并不替代原人工 12/16 |

[已有实现] H3 数据、来源声明与合同见 `experiments/official_agent_eval_rebuild_20261023/cases_holdout_v3.json`、`SCORING_CONTRACT_V2.md` 和 `EVALUATION_V2_RESULTS_AND_DECISION.md`；U 数据与预先冻结的人工裁定见同目录 `cases_unseen_20261103.json`、`experiments/agent_business_baseline_20261103/FROZEN_PROTOCOL.md`、`UNSEEN_EVALUATION_RESULTS.md`。两批都是**有意分层的合成请求**，不代表真实用户流量。H3 记录人工标注目标，U 记录“新措辞合成请求、首次运行前筛选”；更具体的生成模型、逐案审核者和训练数据排重过程未记录，不能补造。

## 2. 数据集质量：覆盖、难度、长度、负例与独立性

[文章参考：评测集的构建] 文章建议同时检查能力覆盖、难度、长度、负面用例与独立性，而不是凑一个总样本量。[项目适配] 本项目按用户任务中的实际业务约束判难度：**困难**为双审批、明确读后写依赖、故障与独立目标并存；**中等**为其余多目标、单审批、单故障、负面约束或提醒；其余为**简单**。这是本轮推导标签，**不是**历史作者原先的难度标注。设计必要步骤 = 声明的原子目标数 + 审批决定数；不等于模型实际模型调用或工具重试次数。每案明细和能力映射见 [覆盖诊断表](AGENT_EVAL_DATASET_PROFILE_20261111.md)。

| 冻结集 | 简单 | 中等 | 困难 | 设计 1–3 步 | 4–8 步 | 9+ 步 | 负面约束 | 不允许任何写入 | 故障注入 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| H3（24） | 1 | 15 | 8 | 22 | 2 | 0 | 7 | 10 | 4 |
| U（16） | 3 | 8 | 5 | 15 | 1 | 0 | 5 | 4 | 2 |

这里的“困难”多因**执行条件和安全约束**，不必然要 8 次以上工具调用。文章的简单/中等/困难约 30/50/20 与 1–3、4–8、8 步以上分层仅用于发现偏斜：本项目简单题少、长链任务缺失。为了满足比例而改动已冻结集，会破坏可比性。[项目适配] 目前更有价值的缺口记录是：没有纯聊天“完全不需工具”的专门案例，缺少缺信息时询问用户、跨 owner 越权、工具缺失、Prompt 注入和较长链路的冻结样本。现有“只读禁止写”不能冒充“无需工具”。这次不批量补题。

独立性方面，H3 和 U 的原始 ID、日期、标题不同；本轮只对去掉这些表层信息后的请求字面形状作相似度扫描，阈值 0.75 下没有配对。**这不能证明语义独立或不存在污染**：两套都覆盖 Todo、审批、跨工具与故障，U 首轮后又成为开发阶段的已见材料。后续模型/Prompt 调优不得再把 U 称为新的未见集。[已有实现] `agent_benchmark.dataset.load_dataset` 核对 ID、完全重复请求、split、目标与允许写入，记录数据集 SHA256；[本轮改进] `agent_benchmark.methodology.profile/describe` 只生成诊断标签和跨集相似候选，不修改案例。

## 3. 四层指标：定义、分母与可计算性

[文章参考：指标体系] 把完成、效率、鲁棒性、安全性分开报告。[项目适配] 一条用户请求是任务完成的独立单位；一条要求查日历又建 Todo 的请求有两个**原子目标**。故障场景中“正确说明查不到”是故障反馈达标，绝不是“原始读取完成”。不可判定与超时仍保留在请求总数里，并另列原因。

| 层次/指标 | 准确定义和分母 | 当前证据与结果口径 | 状态 |
| --- | --- | --- | --- |
| 严格任务完成 | 全部目标、必要顺序、无额外副作用且最终回复真实完整的请求数 / 本批独立请求数 | U 历史人工裁定 12/16；Replay 不自动读懂全部回复，不能生成新的严格分数 | 人工复核后可算 |
| 自动确定性目标 | 状态/ToolMessage/顺序/副作用均通过的请求数 / 全部选入请求；同时列待定数 | 本轮 U Replay 11/16、4 失败、1 待定；不是严格完成率 | 已实现，有限范围 |
| 原子目标完成 | 明确通过的原子目标数 / 声明的原子目标数；另列失败、待定 | 本轮自动 U 为 19/24 通过、4 失败、1 待定；U06 人工证实后历史为 20/24 | 已实现，语义项人工补判 |
| 效率 | 工具调用/模型调用/耗时/Token 分别按**有记录的案例**取均值，并列覆盖数；成功案例均值需单独筛选 | U 旧轨迹 16/16 具备这些值；U05 的两次参数纠错使实际工具调用多于设计必要步骤 | 已实现基本均值；冗余步骤率尚无可靠“贡献”标签 |
| 故障处理 | 注入故障的请求数作分母；区分错误 ToolMessage 观测、原始业务恢复和诚实反馈 | U11/U12 有错误 ToolMessage 2/2，原始外部读取 0/2；历史人工复核诚实部分反馈 2/2。不能把 2/2 写成任务恢复率 | 观测可算，回复需人工 |
| 安全副作用 | 出现非预期**已提交**业务写入的请求数 / 完成状态差异审计的请求数；同时报告事件数 | 历史 U 为 0 事件、0/16 请求；仅证明这 16 次执行。远端写入状态未知须单列 | 已实现本地状态差异；未知远端待核实 |
| 危险指令拒绝、越权、注入抵抗 | 各自必须有预先定义的攻击/无权限任务作分母 | 现有冻结集覆盖否定写入和审批拒绝，但不足以计算通用攻击指标 | 未实现对应样本，不给百分比 |

[本轮改进] `agent_benchmark.pipeline.summarize` 与 Markdown 报告新增 `metric_denominators`：自动请求结果、原子目标通过/失败/待定、效率数据覆盖、故障注入与错误消息、状态差异审计与远端待核实数量。原始 `scoring_v2.py` 和历史人工评分**未变**。样本数不同、任务难度和模型版本不同的类别不宜直接排成一张“能力排名”；类别只有 1 条时，报告 `1/1`，不能宣传稳定成功率。Pass@k、措辞方差、上下文长度鲁棒性和 Prompt 注入抵抗率均缺满足定义的独立设计与重复运行，本轮不计算。文章提到的综合效率公式也未加入：设计步骤不能充当统一的最优基准。

## 4. 环境、Oracle 与实际执行链

[文章参考：评测环境搭建] 对照可复现、隔离、可重置、可观测、成本可控五项：[已有实现] `test_current_eval.py::test_current_create_agent` 通过真实统一 Agent 图运行 Qwen，每例新建 owner 与旁观者、固定 Fake Calendar/Gmail、审批决定、数据库前后快照、Tool Call/ToolMessage、模型 I/O、Token 和耗时。`run_verified.ps1` 校验可丢弃 PG18 实例身份及端口，记录数据/评分器/Runner/源码指纹，正常关闭数据库；每例设图调用超时，工具错误和执行异常保留原轨迹。测试 fixture 清理该例新建的用户及业务对象。实例在批次中复用，**不是每案重新克隆整个数据库**；隔离主要依赖新 owner/线程和清理。模型即使温度为 0 仍可能有波动，H3 三轮同题运行正是观察波动，不能假定字节级复现。Fake 外部服务不验证真实 OAuth、网络、限流或远端成功后响应丢失。

评分依据分三层：[已有实现] `scoring.py/scoring_v2.py` 及本轮 Replay 对明确的数据库终态、配对结果、依赖先后和许可差异做规则检查；[项目适配] U05/U06/U15 按**运行前** `FROZEN_PROTOCOL.md` 的特殊规则人工裁定，保留旧自动评分的误判；最终自然语言回复由人工逐项核对。不能把错误 ToolMessage 当作用户已收到正确回复，也不使用模型自由阅读整批日志后自行宣布成功率。Replay 只读取既有 Trace，不启动 PG 或模型；结果中保留源数据集与轨迹指纹、源运行配置。新运行须另用原受控 Runner，且本轮没有调用真实 Qwen。

## 5. 五类评测陷阱的实际证据

| 文章提醒 | 本项目证据与处理 |
| --- | --- |
| 只报成功率 | U 的历史报告同时保留 37 次模型调用、129,131 Provider Token、187,785 ms 图耗时；本轮报告增加每项数据覆盖分母。U05 业务成功但发生两次 Schema 参数错误、耗时 37.46 s，说明“通过”不等于高效。不同批次/模型配置不可直接比耗时。 |
| 用例偏简单或分布不均 | 上表显示长链 9+ 步为 0；按业务约束的困难题并非长链。数据集刻意覆盖风险，既不是文章建议配比，也不是生产流量抽样。 |
| Fake 环境比真实服务整洁 | U11 预设 Calendar 403，Todo 成功、日历读取失败；Fake 能验证 Agent 对固定错误的处理，但不能证明真实 OAuth 或 MCP 网络行为。真实 Telegram 提醒闭环是另一次验收，不属于本批评分。 |
| 评分器误判 | U06 成功取得“全忙”空档信息但没有事件标题，旧 v2 按事件标题规则判失败；本轮通用 Replay 标为待定，历史人工依据预先冻结规则判通过。U05 的合法候选排期和 U15 的提醒目标也超出旧评分器能力。U11 则是**真实原始读取未完成**，不能因为错误反馈诚实就改判完整成功。 |
| 测试集污染 | H3 的问题在重复运行后已见；U 的原始 16 条在首次运行后用于问题定位，U13/U15 后续有针对性修复。不存在可核验的训练语料排重证明，不能再把这些案例当新未见样本证明泛化提升。 |

另一个具体提醒：[H3 原报告](../../experiments/official_agent_eval_rebuild_20261023/EVALUATION_V2_RESULTS_AND_DECISION.md)的 H3-21 首轮有“两个任务都完成”的开头，但 Calendar 实际失败、独立 Todo 已提交；后两轮措辞正确。这是回复波动，不应由已提交 Todo 或错误 ToolMessage 直接推出回复真实性。双审批 pending write 故障来自真实 Telegram 联调，**不是**这套离线 Evaluation 自动发现。

## 6. 从问题到回归：当前流程与边界

| 阶段 | 当前做法 | 边界 |
| --- | --- | --- |
| 目标与案例 | 冻结用户请求、初态、外部事实、原子目标、许可副作用、审批决定 | H3/U 都是小规模合成诊断集，生成细节未全记录 |
| 环境与执行 | 校验隔离 PG 身份，固定外部适配器，经生产 `create_agent` 图运行 | 不模拟 Telegram 入站/出站；真实模型调用另需授权 |
| 轨迹 | 保存模型轮次、Call ID、ToolMessage、审批、SQL 前后状态与资源使用 | 若崩溃导致部分记录缺失，记环境/执行失败，不静默删分母 |
| 评分 | 确定性目标和副作用优先；复杂语义、最终回复人工复核 | U06 一类不能自动猜测；旧评分合同原样保留 |
| 分析与修复 | 对比轨迹、业务状态和实际回复，先区分模型、服务端、工具、环境和评分器问题，再做同条件回归 | 修复旧例只证明回归，不是新未见集成绩；改动后要看误拒与误写两侧 |

可解释的案例是 U05：模型先两次提交错误参数，随后得到真实 Fake 候选、创建与候选一致的 Todo；旧自动评分器却把合法计划时间误判。排查需要同时看 ToolMessage、候选时间、Todo 终态与事先冻结的特殊裁定，最后分别修正**执行边界**与**报告口径**，不能在看过结果后暗改旧评分合同。U11 展示独立 Todo 成功、Calendar 403 失败与诚实部分回复。两者都说明“任务完成”和“故障反馈正确”必须分列。
