## 2. 本次标签与读表方式

- **难度**：简单＝一个明确目标、没有复杂依赖；中等＝多目标、跨工具依赖或额外约束；困难＝审批、异常处理/恢复、复杂状态变化或多重约束。难度表示*设计负担*，不取决于历史模型是否答对。单项审批仍标困难；读出邮件主题再创建待办通常是中等，不因“读后写”一词自动标困难。
- **任务类型**：单项＝一个主要业务操作，跨工具独立＝多个目标可以分别完成，跨工具依赖＝后续操作必须使用先前读取的事实，多阶段审批＝需要人作决定和恢复。只读负面题仍需要工具，不属于“无工具题”。
- **预期步骤**是简写的合理业务过程，例如“读→建”“提案→批准→删”，不是最少模型调用次数、实际 Tool Call 数，也不包含内部重试。允许不同合法工具路径；最少正确调用次数尚未逐案冻结。
- **Ground Truth（GT）**：`明确` 表示关键业务状态/事实和允许写入可从结构化原题核对；`协议` 表示还需引用首次 U 运行前冻结的特殊规则；`部分` 表示自动判分有歧义或自然语言约束需人工核查。**所有 40 题的最终回复真实性仍需语义复核**，`明确` 不等于整题全自动可判。
- **时间**：`是` 表示明确日历日期或提醒时刻，重跑须固定业务时钟、时区与外部事实；`否` 表示目标不依赖具体时刻。U01 虽说“下周”，同时明确“不设日期”，该措辞的理解仍值得人工复核。

依照第 2 节**重新给出的初步难度规则**，简单 **4/40（10%）**：H3-03、U01、U02、U04；中等 **23/40（57.5%）**：H3-01、02、04～12、17～20；U03、06～10、15、16；困难 **13/40（32.5%）**：H3-13～16、21～24；U05、11～14。此分布不是历史冻结比例，也无需强行调成某个文章建议比例。尤其 H3-09～12 是较轻的事实写入依赖，U05 才包含动态候选、精确窗口和禁止提醒的多重条件。

场景可重叠：**预设外部故障 6 题**（H3-21～24、U11、U12），其中 H3-22 是一次临时失败、另外五题持续或明确拒绝；**审批 6 题**（H3-13～16、U13、U14）；**明确禁止某项业务写入或要求拒绝/保留/防重复的负面题 12 题**（H3-14～20；U06、07、08、14、16）。其余 34 题没有预设外部故障，不能全部称作“简单正常题”。参数 Schema 错误在 U05 首轮 Trace 中出现，**不是预设的异常题**；U16 是同一请求的结果数量限制，不是重复投递实验。

**时间与环境**：有明确日历日期或提醒时刻的 17 题为 H3-05～09、11、19、21～23；U04～06、08、09、11、15。它们须固定 Asia/Shanghai 业务时刻、Fake 日历世界和相应权限；U15 还需固定已有 Todo，审批 6 题需预置目标及决定。H3/U 顶层 `time_reference` 历史上只是记录日期，并非可注入的精确时刻；当前 Runner 已支持显式 `evaluation_now` 与 IANA 时区，**旧题未因此自动获得历史可比性**。U01 的“下周”虽然不形成保存时间，仍有自然语言解释边界。最少正确工具调用次数没有逐案冻结，不能拿 65 个目标数冒充步骤数。

## 6. Ground Truth 与题目有效性

40/40 有可解释的业务意图和可控的合成初态，可保留作项目级诊断题；**不等于 40/40 可以全自动、无歧义判定**。既有[逐案质量审计](AGENT_EVAL_CASE_AUDIT.csv)给 32 题的结构化 GT 标“充分”，U05/U15 为“结构化加冻结协议”，其余六题 H3-21、23、24、U06、U11、U12 有局部判据或语义歧义。本文把所有最终自然语言回复仍列为待语义复核。

| Case | 设计、标注或评分边界 | 可信判据与处理 |
| --- | --- | --- |
| U05 | 动态窗口不能用固定时间猜；旧评分器把合法计划时间误当副作用 | 依据首次运行前协议，先有成功候选，再精确核起止、45 分钟、冲突及提醒为空；旧分数保留 |
| U06 | JSON 要求 `calendar_read.contains` 事件标题，但合法“全忙”工具可不返回标题 | 协议允许 availability/candidate 证明无空档；不能强迫唯一工具路径，也不能改原始 JSON |
| U15 | 旧评分器不认识提醒目标，且必须保持其他 Todo 字段不变 | 协议给精确 `reminder_at`；核字段差异，投递另测 |
| H3-24 | “不可把未知邮件内容编进说明”仅在请求文字中，结构化 `goals` 未完整表达 | 检查真实说明及回复；证据不足留待定，不能只因 Todo 存在自动通过 |
| H3-21、23；U11、U12 | 外部读故障是预置事实，正确反馈与原始读取完成是两回事 | 日历/邮件读取目标失败可与独立 Todo 完成并存；反馈真实性独立复核 |

H3-22 预置一次故障，目标仍是最终取到 Maple 事实。U10 需要邮件**正文**中指定事实，不能用邮件标题替代。审批题要同时核对决定、目标业务终态和禁止副作用，不能只看最终文字或一次工具调用。已提交副作用与模型仅提出的 Tool Call 也必须分开。历史 Agent 执行失败（如 U13 首轮未选审批工具、U15 首轮被执行端误拒）并不使原题无效。

## 7. 现有设计价值、缺口与最小整理建议

**值得面试讲的既有设计**是：H3 先按独立写入、跨域读取、读后写、审批、负面授权、故障处理六层构题；U 首轮前冻结请求、初态及 U05/U06/U15 的特殊裁定；通过数据库前后状态、配对的工具结果、批准/拒绝记录和允许写入清单，而非单看模型说“成功”，判业务目标。U05、U10 能讨论必要依赖，H3-21/U11 能讨论“外部读取失败、独立 Todo 成功”的部分结果。H3/U 都是合成诊断集，只能说明指定受控环境中的能力，不证明线上可靠性。

**主要缺口**：创建 Todo 21 题，普通修改/完成、独立 Google 事件写入、提醒取消均为 0；真正动态候选排期只有 U05，邮件正文条件写入只有 U10；没有主动跨用户越权题、纯无工具澄清题、外部写入结果未知或 Receipt 重投题。故障 6 题不构成超时、429、403、空结果、写入已发后不确定等完整矩阵。近重复能力族包括 H3-01/04、H3-02/U03、H3-09/11、H3-10/12、H3-13/U13、H3-15/U14、H3-21/U11、H3-24/U12。它们不是逐字重复，也不必删除历史记录；但不能各算一项新的能力。

**下一步只需整理，不急于加题**：

1. 保留 H3/U 原始文件、冻结协议、首次 Trace 与旧分数不动；为每题另建轻量元数据表，记业务能力、负面约束、预置故障、时间依赖、GT 来源和人工复核点。本文可作为起点，但本轮没有修改数据集。
2. H3-03、05～08、13～20，U01～04、07～10、13、14、16 等可沿用为开发回归/诊断题；模板近似题可保留作措辞稳定性观察，但报告能力覆盖时聚合。U05、U06、U15 和 H3-24 在**新版本**里优先补明确的合法路径、字段不变、禁编造等 GT；旧版仍按原协议保存。H3-21、23、24、U11、U12 适合同时报告“原始目标”和“故障处理”，不可合成单一成功标签。
3. U 首轮是当时冻结未见；其轨迹后续已用于定位 U13/U15 等问题。新模型/Prompt 的新基线应另留少量从未用于调优的题，冻结生成依据、初态、时间和判据后才执行。不能把重放旧 Trace、更新评分器或换名复制旧题说成新未见测试。
4. 只有准备扩充至约 40～50 条时，才针对真正空白能力少量加题：Todo 修改和版本冲突、提醒取消、Calendar 独立写入与未知结果、跨用户拒绝、无工具澄清。每种先定义可观察的初态与合法终态，避免为凑数换标题。

**面试可诚实表述**：已经完成两批共 40 条合成业务题的分层设计和首轮冻结，覆盖 Todo、Calendar/Gmail 读取、跨工具依赖、HITL、负面写入及固定外部故障；使用业务终态、工具轨迹和人工裁定补足单纯回复判分的不足。**尚未完成**的是全面业务覆盖、统一无歧义的自动 GT、真正新的未见基线、长期独立性证明、真实 Telegram/Google 端到端表现验证。历史 U 首轮结果和现在的 Replay/Judge 分析必须分开叙述。
