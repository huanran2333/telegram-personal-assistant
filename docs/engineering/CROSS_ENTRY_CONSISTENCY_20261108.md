# Telegram 与 Web 交叉入口一致性验收（2026-11-08）

范围：当前统一 `create_agent` 生产链路和 Web 结构化表单。Web 不发起 Agent 任务；它只可处理 Telegram 已产生的审批。以下测试使用隔离 PostgreSQL 和 Fake Calendar，没有访问真实 Google 或 Telegram。

## 共享操作与两种顺序

| 对象及操作 | Telegram 先提交，Web 后提交 | Web 先提交，Telegram 后提交 | 执行边界 |
| --- | --- | --- | --- |
| Todo 查询、日历/Gmail 查询 | Web 下次读取看到数据库或远端当时状态；只读不参与写入竞争 | Telegram 下次读取同理 | 查询结果是快照，不是锁，也不代表后续写入已完成。 |
| Todo 创建 | Web 的创建是另一条新记录；同一 Web 幂等键只创建一次 | Telegram 的创建是另一条新记录；同一 Tool Call 由业务账本防重 | 两个不同入口分别发起的创建没有共同操作 ID，不能按相同标题自动合并。 |
| Todo 修改、完成及计划时间 | Web 使用读取时的 `If-Match` 版本；旧版本返回 412，不覆盖 Telegram 已提交结果 | Telegram 先从本轮成功工具结果取得目标 ID 与版本，再在行锁内比对；旧版本返回配对的错误 ToolMessage，不写入 | 模型填的版本本身不可信；可信版本来自同轮工具结果的非模型可写元数据。Web 与 Telegram 都使用同一 Todo 版本。 |
| 提醒设置、取消；Web 暂停、恢复 | Web 的旧 Todo 版本返回 412，调度版本不被旧请求改写 | Telegram 的旧版本被拒；成功的提醒变更增加 Todo 与提醒版本 | 对已有 Todo，两个入口的提醒变更均不顺带改变计划时间。Web 相同幂等键若换了 `If-Match`，返回 409。已有 occurrence 仍按提醒版本和当前状态核对。 |
| Todo 单项删除及按标签删除 | Web 后续旧版本修改返回 404/412；旧删除重试用原 Web 幂等键返回原结果 | Telegram 审批提案绑定目标及版本；Web 在等待审批时修改或删除，批准后发现目标变化则拒绝旧提案，不删除新状态 | Telegram 删除只由 Telegram 发起 HITL；Web 可处理该审批。审批并不代替 owner 与版本检查。 |
| 独立 Google 事件创建 | 两个独立操作使用各自稳定的 action ID/事件 ID，可分别创建 | 同理 | 同一 Web 幂等键或同一 Telegram action ID 不重复远端写入。跨入口不同请求没有语义去重。 |
| 独立 Google 事件修改、删除 | Web 根据页面读取的 ETag 重新绑定目标，并以原 ETag 条件写入；目标先变则返回冲突或待核实，不覆盖 Telegram 结果 | Telegram 审批提案保存 ETag；Web 先变后，原条件写入不覆盖 Web 结果，并进入原有核实/人工复核路径 | 写入超时仍用现有远端证据与对账处理，不能把未知结果说成确定失败。 |
| Todo 的 Google 时间块 | 修改 Todo 产生新的镜像期望版本；后台只按当前修订及远端 ETag 对账 | 同理；Web 与 Telegram 对 Todo 的改动汇入同一镜像记录 | 两入口的“独立 Calendar 修改/删除”现在会拒绝带 Todo 归属标记的时间块，要求操作对应 Todo。 |
| 会议草稿审核 | Web 按草稿修订号与来源新鲜度核对后更新；旧审核被拒 | Telegram 生成新草稿或来源变化后，Web 旧审核被拒 | Web 审核是草稿状态变更，不是对原 Agent Checkpoint 的任意恢复。 |
| Google 同步开关 | 仅 Web 有该操作；Telegram Todo 写入遵从当前配置及后台再次核对 | 同理 | 关闭不能撤回已发出的远端请求；已存在远端事件不会自动删除。 |

## 本次修复

1. 普通 Telegram Todo 修改、设置和取消提醒原先只有行锁，没有读取版本与写入版本的比较。现在生产工具要求同轮成功查询/创建结果中的目标版本，写入时锁行比对；冲突明确返回“本次操作未执行”。
2. Web 提醒操作的幂等请求摘要加入 `If-Match`；同一幂等键不再能在换版本后重放旧成功。Web 为已有未排期 Todo 设置提醒时也不再自动生成计划时间，与 Telegram 的已验证提醒语义一致。
3. 独立 Calendar 更新/删除原先可选中 Todo 镜像时间块。现在目标绑定阶段检查远端的 Todo 归属标记，两个入口均在写入前拒绝，并提示操作对应 Todo。

## 已验证及不能声称的保证

- 隔离 PG 覆盖 Todo 两种提交顺序、行锁等待后版本冲突、提醒设置与取消、待审删除与 Web 修改，以及 Web/Telegram Calendar 更新和删除的两种顺序。Fake Calendar 覆盖 Todo 镜像时间块禁止独立写入；生产 `create_agent` 图覆盖 Todo 版本元数据通过 ToolMessage/Checkpoint 传递。
- 这不是跨 PostgreSQL 与 Google 的原子事务。日历空档查询与 Todo 排期之间，其他入口或外部用户仍可能改变远端日历；候选来源校验只能证明“模型用的是本轮真实返回的候选”，不能证明该时段从此不会被占用。Todo 镜像可能异步延迟或进入 REVIEW，页面应查看同步状态。
- 不对两个入口分别发出的同一自然语言意图做语义去重；不能把此机制称为端到端 Exactly-Once。未使用真实模型和真实 Google/Telegram 对本次改动做端到端验证。

## 当日真实 Web／Google 定向调试补充

使用当前受保护的本机应用凭据，核对 PostgreSQL 18.6 `personal_assistant` 和已配置的单一 Google 测试 owner。通过真实 Web 路由及临时、已认证的测试会话执行请求，结束后删除临时会话；并未启动 Telegram Bot、运行真实模型或打开实际浏览器。前端 Calendar 测试 2/2 通过，当前源码的 Web 构建通过。

- Web 创建四条带 `DEMO-20261108-` 前缀的排期 Todo，11 月和 12 月各两条；未设置提醒。Web 创建两条独立 Google 事件，各月一条。同步处理器仅领取该 owner 队列里四条样例 Todo 的待同步记录，最终四条镜像均为 `SYNCED`。
- 真实 Web 日历读取：11 月和 12 月分别返回本地排期两条、Google 事件三条（两条是 Todo 镜像）；按页面现有去重逻辑，每月展示三条。尚未在实际浏览器中目视验收。
- 同一条样例 Todo：业务工具先改，携旧 `If-Match` 的 Web 修改得到 412；Web 刷新后修改成功，携旧版本的业务工具返回版本冲突，最终标题和优先级未被旧请求覆盖。这里直接调用了生产 Todo 业务工具，未经过真实 Telegram 消息与模型。
- Google 独立事件：紧接一次成功修改提交旧 ETag 的第二次 Web 请求，**曾返回 200 并覆盖了事件标题**。随后以新 ETag 修正两个样例标题；一个延迟约一秒的旧 ETag Web 请求得到 412，标题保持不变。对同一样例事件直接发送故意错误的 ETag，Google 返回 412。说明远端条件请求通常有效，但本次已观察到紧邻写入的版本可见性窗口；现有实现不能据此声称对任意快速交叉写入都有严格防覆盖保证。样例最终标题已读回正确，风险未通过修改生产代码消除。

这次补充是真实数据库、真实 Google 和 Web 路由级验收；它不是 Telegram→Web 的用户端联调，也不是对长期并发稳定性的统计。完整启动脚本会恢复 Bot／主动通知，因此本次没有为看页面而启动整套服务。
